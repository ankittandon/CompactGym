Teaching a small model what to forget

CompactGym is a practice environment for context compaction. An email and calendar assistant works through a long session, its history gets squeezed to fit a small window, and we check what it forgot.

Environment, 10 baselines, tests: built Live results: small samples Trained model: not yet

We set out to train a small open model that decides when and how to compact, and to beat a frontier model at it. This page records what we built, what the numbers say so far, and where our own claims turned out to be wrong.

The short version: a deterministic method that does no rewriting, called cliff, is very hard to beat on cost and speed. A frontier summarizer forgets less. A popular quality metric points the wrong way. Nobody has trained the small model yet.

The problem

An agent can only hold so much text. When the window fills, something has to be dropped, summarized or moved aside. If the wrong thing goes, the agent forgets an instruction such as "don't email Jonas" and does the wrong thing without any error.

Small windows make this constant. Apple's on-device model has a 4,096 token window shared between the prompt and the answer. Local models run through Ollama default to a few thousand tokens. A real session passes that quickly.

How the gym works

A simulated user works through 28 requests with a frozen assistant model. The assistant has email and calendar tools over a generated mailbox. Early in the session the user states facts that matter later: a person to leave out of the loop, a date that moved, a PO number, a rule about sign-offs. Before each model call, if the context is over budget, a compactor rewrites it.

Hard mode

At 16K almost nothing was forgotten, so there was nothing to measure. Hard mode plants facts in turns 1 to 3 and asks for them only in the last 40% of the session. A forgotten fact is gone for good, because the simulated user never repeats it. A goal scores zero when the fact behind it was violated. That raised newly forgotten facts from 0.2 to about 0.4 per branch.

Branching

Any step can be snapshotted and continued under different compactors with identical seeds. The difference between branches is the effect of the compaction itself, which gives a clean comparison and a ready baseline for reinforcement learning.

What decides the winner

Our reward charges for waiting: 0.002 per second of pause. A summarizer that blocks for two minutes pays about 0.24, while the whole spread in task success between methods is about 0.08. We rescored the same 14 branch points four ways.

So the headline depends on a weight. If compaction runs in the background and nobody waits, the pause term vanishes and a good summarizer is ahead. That is the opening for a trained small model: frontier-level forgetting at a small model's price and speed.

A metric that misleads

InfoLoss measures how much worse a model predicts the next few turns from the compacted context than from the full one. It looked like a natural training signal. We checked it against what actually happened in live branches.

What we got wrong

Several early conclusions did not survive checking. We list them because the corrected picture is more useful than the first one.

The buried-fact test did not test what we meant

We expected facts that live only in a long email body to hurt cliff, since it drops long tool results. They did not: cliff and the frontier summarizer both forgot 0.17 such facts per branch. We first explained this with agents re-reading the email. That was wrong, because we had counted first reads. Re-reads were 0 of 11 for cliff. A likelier cause is our own prompt, which asked the agent for the gist of the email, so the agent restated the fact in its own reply, and cliff keeps assistant text. The test needs redesigning.

Success differences are real when paired

We said success differences between methods were not significant. Paired by branch point, the frontier summarizer beats cliff by 0.08, interval 0.04 to 0.13.

A flaw in our first reward check

We resumed each episode from its earliest eligible point, but some episodes plant their facts late. Those branches had two or three turns left to forget anything, which made forgetting look rarer than it is.

The pilot's best-of-8 number is not reproduced

An earlier pilot reported 41% lower InfoLoss for best-of-8 against one small-model attempt. A later run on 10 new seeds gave 25%. We have not re-verified the pilot figure.

Editing in place

A note on Shelley, the agent from exe.dev, inspired the newest method. A harness nudge asks the model to edit its own history with a tool: trim particular tool outputs, or squish a range of messages into a short note with a pointer to the original. An append-only log keeps everything.

We rebuilt that as edit_context. The model sees the context numbered and replies with edits by index. Every removed original goes into memory, so the assistant can recall it. Bad edits are rejected: protected messages, ranges that cut a tool call off from its result, notes longer than what they replace.

Four branches only. The frontier model edits cleanly and keeps about half the context. The untrained small model fails the protocol in most compactions, and its reasoning makes it slow. That sets the training target.

What is next

  1. Generate training data for the edit format: frontier edits as targets, plus the planted facts as exact labels for what to pin.
  2. Fine-tune a small non-reasoning model on it. The current small model thinks too long to win on latency.
  3. Compare it with the frontier editor on live hard-mode branches, with at least 14 branch points per method and matched cost.
  4. Redesign the buried-fact test so the fact cannot be restated or found by a simple search.
  5. Try the same question on LoCoMo and LongMemEval at a 4K budget, where cliff has no tool results to drop.

What would change our mind: if the tuned small model cannot match the frontier editor on forgotten facts, the opening described above does not exist, and cliff stays the answer.

Limits

  • Samples are small: 12 to 14 branches per method in the charts above.
  • The frontier method is an open large model standing in for a closed one. We have not tested Claude or GPT.
  • Prices in the code are placeholders.
  • The 8K and 16K budgets are far smaller than the windows of current models. They stand in for on-device limits and for the pressure of long sessions.
  • The environment is simulated. Nothing here is a claim about a real mailbox.
  • No model has been trained. Every number above is a baseline or a diagnostic.
